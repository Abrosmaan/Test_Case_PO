# SPEC — Contract Checker (тестовое задание PO, Semantic TextNavigator)

Источники истины при конфликте с кодом, в этом порядке:
1. Этот файл.
2. `docs/ARCHITECTURE.md`.

## 0. Цель и рамки

Локальный прототип для специалиста по закупкам. Он загружает TXT-документы (договоры, допсоглашения, письма, проекты) и видит таблицу по договорам: номер, поставщик, сумма в рублях, срок поставки на дату проверки. У каждого значения есть файл, точная цитата и переход к абзацу.

**Жёсткие ограничения задания:**
- 4 часа на всё, включая README. Порядок этапов = приоритет; не успеваем — режем с конца.
- Запуск локально, без платных аккаунтов и API. Без ключа LLM приложение работает полностью.
- Нельзя вшивать ответы, суммы, даты и результаты по именам файлов. На встрече поменяют одно поле и загрузят новый договор того же формата.
- Не придумывать значения: нет данных → «нет данных».

**Правило изменения условий:** условие меняет только допсоглашение, подписанное обеими сторонами, с датой вступления в силу ≤ даты проверки. Письма, проекты, неподписанные ДС — «предложения, не согласованы», показываются отдельно. Имя файла и порядок загрузки на приоритет не влияют.

**НЕ делать в этой версии:** OCR, PDF/DOCX, произвольный чат, авторизацию, деплой, Docker, Supabase, ORM, красивый дизайн. Не-TXT файл → понятное сообщение пользователю.

## 1. Стек

- Node.js ≥ 22.13 (встроенный `node:sqlite` без флага), TypeScript `strict`.
- Сервер: Fastify (логгер pino встроен). Слушает **только `127.0.0.1`**.
- UI: Vite без фреймворка, одна страница.
- БД: SQLite-файл `data/app.db` (в `.gitignore`), голый SQL, схема создаётся при старте идемпотентно (`create table if not exists`).
- Валидация внешнего ввода и ответов LLM: zod.
- Тесты: vitest.
- Команды: `npm install`, `npm run dev`, `npm test`, `npm run typecheck`, `npm run analyze -- <папка>` (CLI-прогон конвейера без UI).

## 2. Константы

Всё настраиваемое — в `src/config.ts`, хардкод в логике запрещён:
- `CHECK_DATE` (по умолчанию `2026-03-10`, переопределяется из UI и env);
- словари ключевых фраз для классификатора и экстракторов (стоп-слова «аванс», «лимит», «бюджет», «срок оплаты», «приемки»);
- шаблон номера договора;
- настройки LLM (провайдер, модель, таймаут, ретраи).

## 3. Этапы

Каждый этап заканчивается запускаемым проектом, зелёными тестами и коммитом. Следующий этап не начинать без команды человека. По каждому этапу — короткий артефакт `docs/tasks/<NN>-<name>.md`: что сделано, решения, что не решено.

### Этап 0. Каркас (≈20 мин)
- `package.json`, `tsconfig` (strict), Fastify на `127.0.0.1`, Vite, vitest, логгер (§4).
- `.gitignore`: `data/`, `logs/`, `.env`, `.env.*`, `!.env.example`, `Заготовки*/`, `*.pdf`.
- `.env.example` с пустым необязательным `LLM_API_KEY`.
- **Готово:** `npm run dev` поднимает пустую страницу, `npm test` зелёный, лог пишется в консоль и в `logs/app.jsonl`.

### Этап 1. Приём и сегментация (≈30 мин)
- Загрузка нескольких файлов (multipart). Проверка: расширение `.txt`, декодирование UTF-8, затем cp1251; пустой файл; размер ≤ 1 МБ.
- Отказ → понятное сообщение в UI с именем файла и причиной, обработка остальных файлов продолжается.
- Дедупликация по sha256: повторная загрузка того же содержимого не создаёт дубль.
- Сегментация на абзацы: `clause_no` (`2.1`, `3`, null), `line_no`, `start`, `end`, `text`.
- **Готово:** тесты на кодировки, пустой файл, не-TXT, дубль; смещения абзаца точно вырезают его текст из исходника.

### Этап 2. Классификация (≈30 мин)
- `doc_type`: contract / amendment / draft / letter / unknown — по заголовку.
- `contract_no` — из текста, не из имени файла.
- `sign_status`: signed_both / unsigned / unknown; `signed_date`, `effective_date`.
- Противоречивые или отсутствующие признаки → `needs_review` с причиной. Без догадок.
- **Готово:** все 6 файлов классифицированы правильно; файл с переставленным именем классифицируется так же.

### Этап 3. Экстракторы полей (≈50 мин)
- Реестр: `src/extractors/<field>.ts`, единый интерфейс `extract(paragraphs) → Fact[] | Rejected[]`. Поля: `supplier`, `total_amount`, `delivery_date`.
- `Fact`: value, document_id, paragraph_id, quote (точная подстрока исходника), start, end, rule_id.
- `Rejected`: кандидат, который правило отбросило, и причина (например, «252 000 — аванс»). Пишется в трассу (§4), не в таблицу.
- ДС: «Пункт X.Y … изложить в следующей редакции: «…»» → тот же экстрактор по тексту в кавычках, факт с `replaces_clause = X.Y`.
- Ничего не нашли → `no_data` с причиной, если она есть в тексте.
- **Инвариант (тест):** у каждого факта `source.slice(start, end) === quote`.
- Добавление поля = новый файл экстрактора + регистрация. Так проверим себя перед встречей: попробовать добавить `penalty_rate`.

### Этап 4. Разрешение на дату (≈30 мин)
- Для каждого договора и поля: базовое значение → поверх ДС с `signed_both` и `effective_date ≤ CHECK_DATE` по возрастанию даты вступления.
- Остальное (письма, проекты, неподписанные ДС, ДС с будущей датой) → `proposals`.
- Итог: value, status (`действует` / `изменено ДС №N` / `нет данных` / `требует проверки`), цепочка источников, список предложений.
- Документ, не привязанный к загруженному договору → отдельный список «не связаны с договором».
- **Готово:** эталонные тесты §5 зелёные.

### Этап 5. API и UI (≈50 мин)
- `POST /api/upload`, `GET /api/contracts?check_date=`, `GET /api/documents/:id`, `GET /api/debug/trace/:documentId`.
- Таблица: номер, поставщик, сумма, срок, статус, значок «есть несогласованные предложения».
- Клик по значению → исходный текст с подсветкой абзаца, цитата, цепочка изменений («было в договоре → изменено ДС №1»).
- Блок «Вопросы»: 4 кнопки/фильтра (срок по договору; сумма по договору; срок раньше даты + флаг несогласованных изменений). Ответ собирается из тех же данных, что и таблица.
- Поле даты проверки.
- **Готово:** ручной прогон 4 вопросов по эталону §5.

### Этап 6. README и записка (≈30 мин)
Структура — по требованиям задания: установка и запуск, зависимости, примеры, известные ограничения; для кого прототип; 5 вопросов клиенту; допущения; 2 метрики; схема архитектуры; 3 технических решения и компромиссы; 100 000 документов и права доступа; 3 следующих улучшения; отчёт о вайбкодинге (инструмент, 2–3 запроса, ошибка AI и как поймана); фактические затраты времени и оставшиеся задачи.

### Этап 7 (только если осталось время). LLM-фоллбэк
- Вызывается только для `doc_type = unknown` или когда не определён `contract_no`. Только классификация, не извлечение значений.
- Провайдер: бесплатный (Gemini free tier по ключу или локальная Ollama). Нет ключа или провайдер недоступен → документ в «требует проверки», это не ошибка пользователю.
- Таймаут, 3 ретрая с экспоненциальной задержкой, затем фоллбэк.
- Ответ валидируется zod; невалидный → ретрай → фоллбэк. Цитата из ответа должна точно входить в исходник, иначе ответ отбрасывается.
- Результат всегда `classified_by = llm`, `needs_review = true`.

## 4. Логирование и отладка

Цель — по логам за минуту понять, почему в таблице именно это значение. На встрече оценивают диагностику.

- **Формат:** pino, JSON-строки. В `npm run dev` — читаемый вывод в консоль (pino-pretty) и одновременно файл `logs/app.jsonl`.
- **Уровень:** `LOG_LEVEL` из env, по умолчанию `info`; `debug` включает подробную трассу.
- **Корреляция:** каждая загрузка получает `batch_id`, каждый документ — `document_id`; оба поля в каждой строке лога этого документа.
- **Что логируется на каждом этапе конвейера:** `stage` (ingest / segment / classify / extract / resolve / llm), `document_id`, `filename`, результат, `rule_id` сработавшего правила, длительность в мс.
- **Решения, а не только ошибки:**
  - классификация: какой признак сработал (`rule_id`, строка, цитата);
  - извлечение: принятые факты и **отброшенные кандидаты с причиной**;
  - разрешение: какой ДС применён, какой нет и почему (не подписан / дата вступления позже даты проверки / не тот договор).
- **Трасса документа** сохраняется в БД (`trace` по `document_id`), отдаётся через `GET /api/debug/trace/:documentId` и печатается командой `npm run analyze -- <папка>`.
- **LLM-вызовы:** провайдер, модель, длительность, число попыток, результат валидации, хеш промпта. Ключ и полный промпт не логировать.
- **Ошибки:** `error` со стеком и контекстом (`stage`, `document_id`). Отказ на одном файле не роняет батч.
- **Запрещено логировать:** ключи и содержимое `.env`. Полный текст документа — только на уровне `debug`.

## 5. Эталон (дата проверки 10.03.2026)

| Договор | Поставщик | Сумма | Срок поставки | Предложения |
|---|---|---|---|---|
| STN-101 | ООО «Вектор Прибор» | 1 380 000 ₽, изменено ДС №1 | 30.04.2026, изменено ДС №1 | проект ДС №2: 1 450 000 ₽, 10.05.2026 |
| STN-102 | ООО «Контур Электро» | 840 000 ₽ | 20.03.2026 | письмо: перенос на 27.03.2026 |
| STN-103 | ООО «ПромСнаб Сервис» | нет данных (стоимость в Приложении № 1, его нет в комплекте) | 30.04.2026 | — |

Вопросы:
1. Срок STN-101 на 10.03.2026 → 30.04.2026 (ДС №1).
2. Сумма STN-102 → 840 000 ₽.
3. Сумма STN-103 → нет данных.
4. Поставка раньше 01.04.2026 → только STN-102 (20.03.2026); есть несогласованное изменение срока (письмо, перенос на 27.03.2026).

Обязательные тесты-ловушки:
- аванс 252 000 ₽ не становится суммой STN-102;
- 10.04.2026 (срок оплаты) не становится сроком поставки STN-102;
- лимит 600 000 ₽ не становится суммой STN-103;
- письмо и проект ДС №2 не меняют действующие значения;
- переименованные файлы и обратный порядок загрузки дают тот же результат;
- **мутация:** в копии договора меняем сумму или срок → результат меняется; новый договор STN-104 того же формата появляется в таблице;
- если `CHECK_DATE` поставить до 01.03.2026 → ДС №1 не применяется (1 200 000 ₽, 15.04.2026).

Тестовые данные читать из `Test Files/` (путь с пробелом — всегда в кавычках); мутации создавать во временной папке теста, исходники не менять.

## 6. Правила для агента

- Секреты не читать, не логировать, не коммитить. Папку `Заготовки (Не публиковать в Гит)/` не открывать: в ней боевые ключи других проектов.
- Хардкод имён файлов, номеров договоров, сумм и дат в логике запрещён. Всё — из текста или `src/config.ts`.
- Повторная обработка того же файла идемпотентна.
- Ошибка на одном файле не роняет обработку остальных.
- Проект всегда запускается. Сломал запуск — чини в том же шаге.
- После шага: 3–5 предложений простым языком — что сделано и как проверить руками.
- Коммит после каждого рабочего шага, сообщение короткое.

## 7. Definition of Done

`npm run typecheck` и `npm test` зелёные, эталон §5 воспроизводится через UI и через `npm run analyze`, у каждого значения есть источник с точной цитатой, README по §3 этапа 6 готов, артефакт этапа записан в `docs/tasks/`.
