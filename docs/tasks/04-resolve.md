# Этап 4. Разрешение на дату проверки

**Сделано**
- `src/pipeline/resolve.ts`: для каждого договора и поля — базовое значение из договора, поверх него факты-замены из ДС, которые подписаны обеими сторонами, не требуют проверки и вступили в силу не позже даты проверки. Применяются по возрастанию даты вступления.
- Письма, проекты, неподписанные ДС и ДС с будущей датой → `proposals` с причиной. В предложения попадают только значения, которые отличаются от действующих.
- Статусы: `действует` / `изменено ДС №N` / `нет данных` (с причиной из текста) / `требует проверки` (несколько текстов одного договора с разными значениями).
- Цепочка источников: «Договор STN-101, п. 3.1: 15.04.2026 → ДС №1 (новая редакция п. 3.1): 30.04.2026».
- Документы, чей договор не загружен, → список «не связаны с договором».
- `decisions`: какой ДС, проект или письмо применён и почему.
- `npm run analyze -- "Test Files" [--date YYYY-MM-DD]`: файлы, трасса по документам (принятые и отброшенные кандидаты), решения, итоговая таблица с цитатами.

**Решения**
- Разрешение считается при запросе, а не хранится в таблице `resolved`: дата проверки меняется из UI, а пересчёт занимает миллисекунды. На 100 000 документов значения на дату пришлось бы материализовать.

**Как проверить**
`npm test` — эталон §5, 4 вопроса, ловушки, переименование и обратный порядок, дата до 01.03.2026, мутация (меняем сумму и срок STN-102, добавляем STN-104).
`npm run analyze -- "Test Files"` — таблица и трасса в консоли.
