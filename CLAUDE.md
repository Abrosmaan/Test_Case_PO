# Contract Checker

Тестовое задание на позицию Product Owner: локальный прототип проверки условий договоров поставки по TXT-файлам. Пользователь — специалист по закупкам.

Источники истины (при конфликте с кодом правы они, в этом порядке):
1. `docs/SPEC.md` — требования, этапы, эталон, логирование.
2. `docs/ARCHITECTURE.md` — конвейер и модель данных.

## Стек
- Node ≥ 22.13, TypeScript strict, Fastify (только 127.0.0.1), Vite без фреймворка, `node:sqlite` (`data/app.db`), zod, vitest, pino.

## Команды
- `npm run dev` — сервер и UI
- `npm test` / `npm run typecheck`
- `npm run analyze -- "Test Files"` — прогон конвейера с трассой в консоль
- `npm run test:e2e` — e2e в браузере (Playwright), своя база и порты
- `npm run cases` — расширенный набор `Test Cases/` против `expected.json`; «молча неверно» = код выхода 1

## Правила
- Не открывать `Заготовки (Не публиковать в Гит)/` и `.env*` — там боевые ключи.
- Значения только детерминированно из текста. LLM — опциональный классификатор неизвестных документов, её результат всегда «требует проверки».
- Ничего не вшивать под имена файлов и конкретные документы. Константы — только в `src/config.ts`.
- У каждого факта точная цитата: `source.slice(start, end) === quote`.
- Логирование по SPEC §4: каждое решение конвейера с `rule_id`, отброшенные кандидаты с причиной.
- Ошибка одного файла не роняет батч. Повторная загрузка идемпотентна.
- Не уверен — «требует проверки» с цитатой, а не догадка. После изменения правил прогонять `npm test` и `npm run cases`: молча неверных значений должно быть 0.
- Перед коммитом смотреть `git status`: не добавлять чужие папки и файлы без спроса.
- НЕ делать: OCR, PDF/DOCX, чат, авторизацию, деплой, Docker, Supabase, ORM.

## Стиль работы
- Этапы SPEC §3 по порядку; следующий этап только по команде человека.
- Проект всегда запускается. После шага — 3–5 предложений: что сделано, как проверить руками.
- Коммит после каждого рабочего шага. Артефакт этапа — `docs/tasks/<NN>-<name>.md`.
