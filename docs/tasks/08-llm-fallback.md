# Этап 7. LLM-фоллбэк

**Сделано**
- `src/llm/providers.ts`: Gemini (ключ из `LLM_API_KEY` передаётся заголовком, не в URL) и локальная Ollama. Нет ключа или `LLM_PROVIDER=none` → провайдера нет, это не ошибка.
- `src/llm/classify.ts`: промпт только для классификации (тип, номер договора, цитата). Таймаут на попытку, 1 попытка + 3 повтора с экспоненциальной задержкой. Ответ: JSON → zod-схема → цитата и номер договора должны дословно входить в исходный текст. Невалидный ответ → повтор → отказ.
- `src/llm/fallback.ts`: вызывается после правил только для документов с `doc_type = unknown` или без номера договора. Результат: `classified_by = llm`, `needs_review = 1`, подсказка с цитатой в `llm_suggestion`. Если LLM недоступна или не дала валидного ответа, документ остаётся «требует проверки» с причиной.
- Разрешение: документы, классифицированные LLM, не попадают в таблицу и не меняют договоры — они в списке «не связаны с договором» с подсказкой модели.
- Подключено в загрузку (`POST /api/upload`), старт сервера и `npm run analyze`. В UI — статус LLM и цитата модели у документа.
- Логи и трасса (`stage = llm`): провайдер, модель, номер попытки, длительность, результат проверки, хеш промпта. Ключ и полный промпт не пишутся (это проверяет тест).
- Новые колонки БД добавляются к старой базе автоматически (`alter table` при старте).

**Тесты** (`tests/llm.test.ts`, фейковый провайдер): валидный ответ и ответ в ```json; отказ на не-JSON, неверной схеме, выдуманной цитате и выдуманном номере договора; повторы после мусора и HTTP-ошибки; таймауты → 4 попытки → отказ; LLM вызывается только для нераспознанного документа, эталонная таблица не меняется; без провайдера — «требует проверки» без ошибки; ключ не попадает в объект провайдера.

**Не решено**
- На настоящих Gemini и Ollama не прогонялось: в среде разработки не было ключа и локальной модели.
- ~~Загрузка ждёт ответа LLM.~~ Исправлено: LLM в фоне, см. `11-llm-background.md`.
- Ответы не кешируются: после перезапуска сервера LLM вызывается заново.
- Подтверждения подсказки LLM в UI нет.

## Живая проверка (Ollama, qwen3:8b, MacBook Air M5, 16 ГБ)

Прогон `npm run analyze` по эталонным файлам и двум нераспознанным документам:
- «Соглашение о поставке № STN-105» → LLM: contract, STN-105, цитата заголовка. Попытка 1 — валидно.
- «Уведомление об отгрузке … по договору STN-101» → LLM: letter, STN-101. Попытка 1 — валидно.
- Оба документа — в «не связаны с договором» с подсказкой, эталонная таблица не изменилась.

**Найдено и исправлено**
- Приложение не читало `.env`, хотя README это обещал. Теперь `.env` загружается при старте; переменные окружения важнее.
- qwen3 по умолчанию «рассуждает»: ~28 с на вызов, при таймауте 15 с каждая попытка падала бы. Провайдер Ollama теперь передаёт `think: false`: ~2–4 с на документ. Модели без рассуждений этот параметр игнорируют (проверено на mistral).
- Формулировка «Договор к договору STN-105» → «Договор STN-105».
- Модель Ollama по умолчанию — `qwen3:8b` вместо `llama3.2`.
